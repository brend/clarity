# Clarity — System Architecture

## Overview

Clarity is a desktop Oracle SQL client. The architecture separates all platform-agnostic logic
(database access, file I/O, profile storage, AI integration) into a **Rust core process**, and
places all native UI in a thin **host layer** written in the platform's preferred language and
toolkit.

The first host implementation targets **Windows**, using **WinUI 3 + C#**.

Future host implementations (same Rust core, different UI layer):
- **macOS** — Swift + AppKit / SwiftUI
- **Linux** — Rust + GTK 4, or a Tauri wrapper

## IPC Mechanism

### Recommendation: newline-delimited JSON-RPC 2.0 over stdin/stdout

The C# host spawns the Rust core as a child process. All communication flows through stdin
(C# → Rust) and stdout (Rust → C#). Each message is a single JSON object followed by `\n`.

**Why stdin/stdout over a named pipe:**
- No port allocation or naming conflicts
- Simpler process lifecycle: when the host process dies, stdin closes and the core exits
- Equally testable from the command line: `echo '{"jsonrpc":"2.0","id":1,"method":"db.connect",...}' | clarity-core`
- No firewall or antivirus interception

**Alternative considered: Windows named pipe**
If stdin/stdout proves too restrictive (e.g., if the Rust core needs to write diagnostic output to
stdout), switch to a named pipe. The pipe name would be generated by the host and passed to the
core as a command-line argument: `clarity-core.exe --pipe \\.\pipe\clarity-<pid>`. The JSON-RPC
framing remains identical.

### Protocol: JSON-RPC 2.0

Standard spec: https://www.jsonrpc.org/specification

All messages (requests, responses, notifications) are single-line JSON objects.

**Request (C# → Rust):**
```json
{"jsonrpc":"2.0","id":42,"method":"db.connect","params":{"provider":"oracle","connection":{...}}}
```

**Success response (Rust → C#):**
```json
{"jsonrpc":"2.0","id":42,"result":{"sessionId":1,"displayName":"hr@//localhost:1521/XEPDB1 [HR]","schema":"HR","provider":"oracle"}}
```

**Error response (Rust → C#):**
```json
{"jsonrpc":"2.0","id":42,"error":{"code":-32000,"message":"Oracle Client libraries not found (DPI-1047)","data":{"kind":"oracleClientMissing","message":"..."}}}
```

**Notification (Rust → C#, no `id`, no response expected):**
```json
{"jsonrpc":"2.0","method":"event.schemaExportProgress","params":{"processedObjects":10,"totalObjects":84,...}}
```

### Error codes

| Code | Meaning |
|------|---------|
| -32700 | Parse error (invalid JSON) |
| -32600 | Invalid request |
| -32601 | Method not found |
| -32602 | Invalid params (validation failure) |
| -32000 | Application error (DB error, file error, etc.) |

Domain-specific errors include a `data` object with a `kind` discriminant:
- `"kind": "oracleClientMissing"` — Oracle Instant Client not found
- `"kind": "general"` — all other errors

## Process Lifecycle

1. **Startup:** C# host launches `clarity-core.exe` with no arguments (or `--pipe <name>` if using
   named pipe). The core writes a single startup confirmation line:
   ```json
   {"jsonrpc":"2.0","method":"event.ready","params":{"version":"0.1.27"}}
   ```
   The host must wait for this notification before sending requests.

2. **Operation:** C# sends requests, Rust responds. Requests are processed sequentially per
   session (one DB operation at a time per session ID). The overall server handles all sessions
   concurrently using async/threads.

3. **Shutdown:** C# closes stdin (or sends a `{"jsonrpc":"2.0","id":n,"method":"system.shutdown"}` 
   request). The Rust core performs graceful shutdown (disconnect all sessions, flush files) and
   exits with code 0.

4. **Crash recovery:** If the core process exits unexpectedly, the C# host detects the closed
   pipe/stdout and displays an error dialog, then offers to restart.

## Responsibility Boundaries

### Rust Core owns

| Concern | Detail |
|---------|--------|
| Database connections | Oracle driver, connection pool (one connection per session), session registry |
| Query execution | SQL parsing for type detection, row fetching, result serialization |
| DDL operations | CREATE OR REPLACE compilation, diagnostics fetch |
| Schema introspection | ALL_OBJECTS, ALL_SOURCE, ALL_TAB_COLUMNS queries |
| Schema search | ALL_SOURCE, DBMS_METADATA text search |
| Schema export | DDL export to .sql files with progress events |
| Profile persistence | JSON file in app data directory, legacy migration |
| Password storage | Platform keychain (Windows Credential Manager via `keyring` crate) |
| AI integration | HTTP call to OpenAI-compatible API, system prompt, response parsing |
| File name sanitization | Platform-specific forbidden characters handled per OS |
| Validation | All input validation before any DB or file operation |

### C# Host owns

| Concern | Detail |
|---------|--------|
| All WinUI 3 windows and controls | MainWindow, panels, dialogs, toolbar |
| Native file dialogs | `IFileOpenDialog` / `IFileSaveDialog` (WinRT APIs) |
| App menu | WinUI 3 `MenuBar` with keyboard accelerators |
| Theme | Reads Windows system theme; applies to WinUI 3 `ElementTheme` |
| Key binding recording | Captures `KeyDown` events, stores as JSON in app settings |
| Query sheet persistence | App-local JSON file (equivalent of localStorage) |
| User settings persistence | App-local JSON file (fonts, theme, AI flags, key bindings) |
| Auto-updater UI | ContentDialog for update download/install |
| SQL syntax highlighting | Third-party WinUI 3 compatible code editor control |

## Platform Extension Pattern

Adding a new platform (e.g., macOS) requires only:
1. A new host process (Swift app) that speaks the same JSON-RPC protocol
2. The identical `clarity-core` binary (compiled for the target OS)

No changes to the Rust core are required for a new UI platform unless new features are added.
The Rust core is cross-compiled per platform as part of CI.

## Key Design Decisions

**One session per connection (current):** `sessionId` is an integer that maps to one live DB
connection. The architecture supports multiple concurrent sessions (multi-connection) but the UI
currently exposes only one.

**Synchronous commands, async streaming:** All commands return a single JSON-RPC response. The
schema export command returns immediately with a result, but *also* emits progress notifications
while running. The C# host must handle interleaved responses and notifications.

**No shared memory:** The IPC channel is the only communication pathway. The Rust core holds no
UI state; the C# host holds no DB state. This makes each layer independently testable.
